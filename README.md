# Mobile Breeze TTS

把 **3.5B 参数**的 [Breeze TTS 2](https://github.com/pcloth/Breeze-TTS-2.cpp) 完整跑在 Android 手机本地：
**纯 CPU、完全离线、导入一个 `.gguf` 就能用**。不需要 PC 转换，不需要清单文件，不需要联网。

克隆任意音色、用一句话"设计"出一个音色、用自然语言指挥情绪、写多角色剧本让它自己换人念——
推理全程在设备上完成，文字与音频都不出手机。

`Android 13+` · `arm64-v8a` · `Kotlin + Jetpack Compose` · `C++17 + ggml` · `全离线`

---

## 为什么值得看

手机端 TTS 不缺"能出声"的方案，缺的是**能改语气、能克隆、还能离线**的那一档。这个项目解决的是后者：

| 常见做法 | 本项目 |
| --- | --- |
| 系统 TTS：音色固定，情绪只有"快/慢/高/低" | 自然语言指令直接控制语气：*"压低声音，带一点疲惫，句尾往下掉"* |
| 云端 TTS：要联网、要计费、文本上传 | 全程本地推理，飞行模式下可用 |
| 小模型端侧方案：音质与克隆效果受限 | 3.5B 全量模型 + 15 步自回归深度解码 + 24 kHz 声码器 |
| 需要 PC 预先量化/转换 | 直接吃 GGUF，模型页下载即用，也能导入本地文件 |

技术上真正难的不是"把 C++ 编进 APK"，而是**让一条 4 阶段的 3.5B 自回归管线在手机上跑到能用**。
仓库里 `docs/` 下 100+ 篇记录基本都是这件事的账本：每一版为什么改、改完快了多少、哪条路走不通。

## 功能

### 合成（三种模式）

| 模式 | 说明 |
| --- | --- |
| **单人朗读** | 输入文本 + 音色 + 情绪描述，流式生成并播放 |
| **多角色对话** | 按 `【角色名】(情绪): 台词` 逐行写剧本，每句自动切到同名音色，句间留 260 ms 换人停顿，最后合成一个 WAV |
| **音色转换** | 保留源音频的节奏与语气，把音色换成目标音色；可开启"保留旋律"（把前 1–2 个声学码本原样搬过来，音高起伏跟着走） |

配套细节：

- **内联语气事件**：`[笑] [叹气] [咳嗽] [清嗓子]` 写在台词里，模型会在那个位置发声道；
- **情绪预设**：内置六条种子，可改可删可存新的，单击套用、长按就地编辑；
- **AI 写语气 / AI 扩写**：接你自己配的 OpenAI 兼容接口，让模型先把"该怎么念"或"该念什么"写出来（这一步联网，语音合成本身仍在本机）；
- **实时 RTF** 与逐帧进度；生成中可随时停止（每帧检查取消，不是只在 flush 时检查）；
- 结果可播放、拖动、重播、导出 WAV，导出命名统一为 `音色名_台词前十字_0001.wav`。

### 音色

- **克隆**：参考音频支持 WAV / MP3 / M4A / AAC / OGG / FLAC，`MediaCodec` 统一转成 24 kHz 单声道 PCM；文本稿由 **SenseVoice 离线 ASR** 自动转写，也可手改；
- **设计**：只写描述（年龄、性别、音色质感）就能造一个不存在的音色；
- **锁定**：设计出来的音色每次都会有点不一样——录一条满意的试听样本，把它的码本留下来，之后这个音色就固定了，情绪仍然可以自由改；
- 音色带**头像与性别**（男女分栏网格、可裁剪头像），列表一眼能认。

### 收藏与历史

生成满意的一段点"收藏"才进收藏夹（默认不入库，避免堆垃圾）；收藏页支持多选、全选/反选、批量导出与删除。

### 设置

| 分组 | 内容 |
| --- | --- |
| 推理引擎 | 运行状态、后端、计算后端与量化内核、线程数（1–8，即时生效）、CFG 指令遵从强度（默认 4.0）、极速模式、启动预热 |
| 模型 | 多档位下载 / 断点续传 / 文件头校验 / 切换使用 / 删除 / 导入本地 GGUF |
| 离线 ASR | SenseVoice int8（239 MB）或 FP32（938 MB），下载后本地识别 |
| AI 接口 | 多家厂商模板 + 自定义 OpenAI 兼容地址，可存多条、只启用一条 |
| 存储 | WAV 导出目录（SAF）、缓存清理 |
| 语言 | 跟随系统 / 中文 / English，改完立即生效 |
| 性能诊断 | 默认隐藏，在"关于 → 版本"连点 6 次解锁；含每阶段耗时、码本截断对照实验 |

## 技术栈

| 层 | 选型 | 说明 |
| --- | --- | --- |
| UI | Kotlin 2.0.21 + Jetpack Compose（BOM 2024.09）+ Material 3 | 单 Activity，4 个 Tab；固定深色主题，金 `#D8B27E` + 近黑 |
| 状态 | ViewModel + `StateFlow` + 协程 | 引擎状态机、生成进度、播放进度全走单向数据流 |
| 推理桥 | C++17 + JNI + CMake 3.22.1（NDK 27.1） | `libbreeze.so` 只是一层桥：参数透传、分阶段线程、取消、后端查询 |
| 推理内核 | [Breeze-TTS-2.cpp](https://github.com/pcloth/Breeze-TTS-2.cpp) + ggml | `libbreeze_gguf.so` + `libggml*.so`，纯 CPU，ARM `dotprod + i8mm + fp16` |
| 音频 | `AudioTrack` 流式播放 + `MediaCodec` 解码 | 8 秒缓冲 + 自适应预缓冲；float32 分块回调转 PCM16 |
| ASR | sherpa-onnx + SenseVoice | 中英日韩粤，中文带标点，抗噪 |
| 诊断 | LiteRT 2.3.2（仅 GPU 可行性探测） | 只用来量"手机 GPU 到底能不能加速这条链路"，不参与正式推理 |
| 构建 | AGP 8.7.3 / Gradle 8.9 / JDK 17 | `minSdk 33`、`targetSdk 35`、仅 `arm64-v8a` |

规模：47 个 Kotlin 文件、约 2.2 万行；JNI + 引擎桥约 1.8 千行 C++。

## 架构

```
Kotlin / Compose
  合成 · 收藏 · 音色 · 设置
        │  BreezeEngine.kt ──── JNI
        ▼
libbreeze.so                     桥接层：cfg / 线程 / 分阶段 / 取消 / 后端名
        │  breeze_init / set_threads / warmup / generate (C API)
        ▼
libbreeze_gguf.so                Breeze-TTS-2.cpp
   ├─ GGUF 读取 + tokenizer + 长文本切分
   ├─ T5Gemma2 文本编码器
   ├─ Qwen3 主干（KV cache；开 CFG 时两份）
   ├─ 15 步帧内深度解码器（15 × 自回归码本）
   ├─ Mimi codec 编码（克隆）/ 声码器解码 → 24 kHz
   └─ ggml CPU 后端（ARM dotprod / i8mm / fp16）
        ▲
models/<档位>/model.gguf         单文件 2.4 – 5.9 GB，可同时装多个

旁支：sherpa-onnx + SenseVoice（离线 ASR，克隆时转写文本稿）
      MediaCodec → 24 kHz PCM WAV（任意格式参考音频归一）
```

音频以 float32 分块回调（可调块大小），JNI 转 PCM16 后交给 `AudioTrack`。

## 一条 3.5B 自回归管线，在手机上花在哪

单条实测（60 字中文、6 线程、极速模式、cfg 1.0）：

| | 预填 | 主干 | 深度解码 | 声码器 | 墙钟 | RTF |
| --- | --- | --- | --- | --- | --- | --- |
| 冷启动 | 768 ms | 979 ms | 3143 ms | 491 ms | **5.76 s** | 2.25 |
| 命中参考前缀快照 | 122 ms | 966 ms | 3126 ms | 479 ms | **4.84 s** | 1.89 |

逐帧账本（一帧 ≈ 80 ms 音频，即 12.5 Hz 帧率）：

| 段 | 每帧 | 占比 | 带宽 |
| --- | --- | --- | --- |
| **深度解码** | **97.7 ms** | **65%** | 54.4 GB/s（达峰值 68 GB/s 的 80%）|
| 主干 | 30.2 ms | 20% | 46.7 GB/s（69%）|
| 声码器 | 15.1 ms | 10% | — |

结论很直白：**短板是内存带宽，不是算力**。深度解码每帧要把同一份 333 MB 权重读 15 遍（15 个码本逐个自回归），
5.31 GB/帧是结构决定的，所以这个项目的优化重点一直是"少读一遍"，而不是"多开几个核"：

- **参考前缀 KV 复用**：一段 prompt 的前半段（参考文本 + 参考码本）只由音色决定，换句子也不变。把它算出的 K/V 存下来，下一句直接把位置指到前缀末尾——逐位相同，不是近似。预填 768 → 122 ms，墙钟 −16%。
- **参考码本缓存**：参考音频不再每次重过 Mimi encoder，每句省下固定 4.1 s。
- **i8mm repack**：权重按 8 行交错装进 repack buffer，`q4_K_8x8_q8_K` 这些内核才真被调用（此前一直是死代码）。加载时用磁盘原始字节对拍，布局不对自动退回普通路径。
- **分阶段线程**：prefill 用满线程跑大 GEMM，首个音频块吐出后降到 2–4 线程跑逐帧 decode，减少屏障空转与降频。
- **收尾**：模型说完最后一个字会继续空转全 pad 帧，每帧照样跑主干 + 深度解码。现在连续 16 帧空帧即收尾，播放尾音的等待挪到后台线程。
- **流式与预缓冲**：声码器每次 flush 都要重算 88 帧上下文，块太小等于白算（25 帧块有 4.5 倍冗余）。块提到 64 帧、播放端按上次实测 RTF 自适应预缓冲（`2000 + (RTF−1)×6000` ms，上限 12 s），把周期性卡顿换成一次起始等待。

这些都是**真机量出来的**，不是估算；走不通的路也留在仓库里：Vulkan 后端已整体移除（提速上限按 Amdahl 推只有 1.3×，而 device 初始化必崩），
NPU 路线做过完整评估（GGUF 量化格式 + 四阶段自回归 + QNN 算子覆盖，短期不划算），每一项都有对应的 `docs/` 编号可以翻。

## 模型档位

GGUF **自带 codec，单文件即可推理**：

| 档位 | 大小 | 说明 |
| --- | --- | --- |
| `q4_k` | ~2.4 GB | 默认推荐，占用最小 |
| `q6_k` | ~2.9 GB | 音质 / 体积折中 |
| `q8_0` | ~3.3 GB | 上游推荐，接近 F16 |
| `f16` | ~5.9 GB | 未量化，明显更慢 |

两个坑：不要用 `-dd2 / -dd4` 变体（连深度解码器一起量化，误差沿帧累积）；
打包时**不含 codec** 的第三方 GGUF 会导致初始化失败。

## 构建

环境：JDK 17+、Android SDK 35 / Build-Tools 35.0.0、NDK 27.1.12297006、CMake 3.22.1、Gradle 8.9+。

```bash
# 1) 交叉编译 GGUF 运行时（纯 CPU + ARM 量化内核，so 自动进 jniLibs）
ANDROID_HOME=/path/to/android-sdk ./tools/build_breeze_android.sh

# 2) 构建 APK
cd app
./gradlew :app:assembleRelease
```

只改 Kotlin / JNI 业务代码时不需要重跑第 1 步（预编译 so 与 C API 头文件随仓库提供）。

## 已知限制

- 只出 `arm64-v8a`，基线是 12 GB 内存 / 骁龙 8 Elite / Android 13+，不迁就低端机；
- `breeze_context` 不可重入，同一时刻只跑一个合成任务；
- 每次生成仍会重建 KV cache 与计算图（上游实现所限）；
- 开 CFG 需要两份 KV cache，F16 档位 + 长文本在大内存机型外会吃紧；
- RTF 约 1.9–2.3，生成速度慢于播放速度，靠预缓冲隐藏，长文本首声仍要等。
